# Chromaflow2 代码结构梳理与调整建议

梳理日期：2026-09-10

范围：`chromaflow2` 项目。本文记录重构目标；2026-09-10 已按此结构完成首轮源码迁移。

## 1. 结论

当前大部分业务代码适合统一放入 `src/`。项目根目录主要保留 HTML 入口、依赖清单、工程配置和文档；构建产物与依赖目录也留在根目录。

迁移前的结构能够运行，但业务源码散落在根目录，`src/` 反而主要用于放测试和环境声明，目录名称无法准确表达职责。本轮已沿用现有页面和组件划分完成整理，未引入复杂的分层框架。

本轮已完成四项调整：

1. 将业务源码、样式、语言文案、文章内容和类型声明归入 `src/`。
2. 把 `profile` 改成能反映当前功能的 `History`，区分本地存储、应用配置和 React Hook。
3. 将跨模块使用的类型从页面、组件中移出，减少反向依赖。
4. 同步修正入口、Tailwind 扫描范围、测试引用和类型声明，保持现有功能及本地数据不变。

| 问题 | 当前证据 | 建议 |

## 5. 文件应放在哪里

### 根目录与 src 的边界

| 文件类型 | 放置位置 | 说明 |
| --- | --- | --- |
| Vite HTML 入口 | 根目录 `index.html` | 保持现有 Vite 项目根目录，调整其中的源码入口路径即可 |
| React 入口、路由、页面和组件 | `src/` | 构成应用运行代码 |
| 颜色算法、存储、语言规则和配置 | `src/` 对应职责目录 | 即使不渲染 UI，也属于应用源码 |
| 全局样式 | `src/styles/` | 由入口文件导入 |
| 当前知识库 Markdown | `src/content/` | 通过 `?raw` 导入并参与构建，是产品内容 |
| 开发说明、方案和验收记录 | 根目录 `docs/` | 面向维护者，不作为知识库文章展示 |
| 依赖、构建和测试配置 | 根目录 | 工具读取这些文件来构建、检查项目 |
| 普通模块单元测试 | 与被测模块同目录 | 便于同步维护，例如本地历史存储测试 |
| 跨模块和工程入口测试 | 根目录 `tests/` | 对应页面组合、HTML 入口等整体行为 |

### assets 与 public 的边界

当前建议将 `favicon.svg` 移到 `src/assets/`，由根目录 HTML 引用并参与 Vite 构建。这与当前图标经过构建处理的方式一致。

`public/` 适合需要原样复制、固定文件名的资源，例如以后可能增加的 `robots.txt`。当前没有必要为了目录齐全创建空 `public/`。也不要把通过 `?raw` 导入的文章直接放入 `public/`，否则会改变文章的加载方式。

### types 的边界

共享业务类型放入 `src/types/`，组件独有的 Props 仍放在组件文件内。

`PracticeRecord` 是实际存入 localStorage 的结构，`HistoryItem` 是历史卡片的展示结构；可以归到同一个历史类型文件，但保留二者区别，不把持久化数据与显示数据强行合成一个类型。

当前 `types.ts` 中还有 `NavLink`。迁移时检查真实引用：未使用则删除，仍有使用则放在所属模块，不应为了迁移而无条件保留旧类型。

### metadata.json 的处理

当前源码与构建配置中未检索到 `metadata.json` 的引用。其内容包括应用名称、描述和 `requestFramePermissions`，不属于当前应用的 Vite 配置。

建议列为待清理文件：确认外部托管或导入流程没有读取它后再删除，不必搬入 `src/`。仅凭源码未引用，不能断言所有外部流程都不需要它。

## 7. 搬迁时必须同步修改的配置

### 7.1 HTML 与 React 入口

根目录 `index.html` 的模块入口由 `/index.tsx` 改为 `/src/main.tsx`；图标引用指向 `/src/assets/favicon.svg`。`main.tsx` 改为导入 `./styles/index.css`。

继续保留 `vite.config.ts` 的 `base: "./"` 和应用的 HashRouter。不要通过把 Vite 的 `root` 改为 `src` 来实现整理，否则 HTML、资源和输出目录的基准也会改变。

### 7.2 Tailwind 扫描路径

当前配置依赖根目录旧布局。迁移后应覆盖：

```js
content: ["./index.html", "./src/**/*.{ts,tsx}"]
```

遗漏这项可能出现“构建成功，但页面样式大面积消失”的问题，因此必须检查构建后的页面样式。

### 7.3 TypeScript 与路径别名

第一轮可以继续使用相对导入，不必同时替换全部引用风格。

若使用 `@/`，TypeScript 的 `paths` 应将 `@/*` 指向 `./src/*`；Vite 的 `resolve.alias` 也要将 `@` 指向同一个目录。当前有独立 `vitest.config.mjs`，不能假设它会自动继承 Vite 的别名，需要同步或明确合并配置。

类型检查范围要包含 `src`、`tests` 和需要检查的工程配置。不要只保留 `src`，导致测试文件意外退出类型检查范围。

### 7.4 文章与测试路径

`knowledgeBaseData.ts` 当前通过 `../../content/...md?raw` 导入文章。移到 `src/data/` 后，路径相应变为 `../content/...md?raw`。

`indexHtmlSeo.test.ts` 从当前 `src/` 移到根目录 `tests/` 后，读取 HTML 的 `../index.html` 仍然成立；不要机械地给所有相对路径增加同一层级。移到 `tests/integration/` 的页面测试则需要重新定位业务源码。

### 7.5 数据兼容性

目录整理不能改变 localStorage 的 `chromaflow2.history.v1`、`chromaflow2.locale`，也不能无故改变记录字段、50 条上限和记录更新事件。

验证历史兼容时，需要保持相同协议、域名和端口。更换开发端口后读取不到原记录，是浏览器存储隔离，不一定是代码迁移导致的数据丢失。

## 8. 建议实施顺序

1. **记录基线。** 运行现有测试、类型检查和构建，记录已知问题；保留同源浏览器中的测试记录，用于检查迁移后的读取情况。
2. **集中源码。** 先将业务目录整体迁入 `src/`，迁移入口、样式、图标和声明文件，同步 HTML 与 Tailwind 配置。
3. **整理职责和命名。** 调整 `History`、`storage/`、`config/`、`hooks/`、`data/`、共享类型及对应引用，保留现有路由地址和数据协议。
4. **整理测试。** 模块测试随模块迁移，跨模块测试进入 `tests/`；验证 Markdown 导入、测试文件读取路径和类型检查范围。
5. **检查旧文件。** 确认根目录不再残留第二份业务源码、重复声明或无效旧引用；按实际使用情况处理 `metadata.json`。
6. **更新文档并验收。** README 中的路径、配置说明和目标目录保持一致。

每一步保持项目可运行。不要在同一轮同时重写算法、更换路由方式、引入全局状态库或改变存储格式，这些工作可以独立评估。

## 9. 验收标准

执行：

```sh
npm test
npm run typecheck
npm run build
npm run preview
```

除命令通过外，还需检查：

- 首页、练习页、历史页、知识库、联系和说明页面均可访问。
- 中英文切换以及从首页重新进入时的语言选择保持正常。
- 提交练习后保存记录，刷新仍可查看，超过 50 条时只淘汰最旧记录。
- 原有本地记录可读取，历史筛选、分页和清空行为保持一致。
- 图片取色与色板操作没有因为资源路径变动而失效。
- 生产构建中的图标、全局样式和 Tailwind 样式正常，子目录部署可访问。
- 没有新增 PHP、API Key 或后端接口依赖。
- 根目录不再同时保留旧 `pages/`、`components/` 等业务源码副本。

当前页面测试使用静态渲染，不能替代浏览器里的点击、刷新、存储和移动端布局验证。正式搬迁后应分别记录自动化检查与浏览器检查结果。

## 10. 当前不需要引入的结构

现阶段没有必要将所有功能再包装成 `features/*`，或引入 `domain/application/infrastructure` 等多层目录。项目规模较小，页面、组件、本地存储、工具和内容已经可以表达主要职责。

若未来练习、历史、知识库各自拥有大量独立状态、Hook、数据层和测试，再考虑按业务模块聚合。当前先让文件位置与实际职责一致，就能明显改善维护体验。
